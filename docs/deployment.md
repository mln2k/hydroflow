# Учебное размещение: Render Free + Neon Free

Состояние на 28.10.2026: конфигурация подготовлена, публичная установка **не создана**. Нет предоставленных аккаунтов/сессий Render и Neon. GitHub-доступ не предоставляет доступ к этим площадкам. Рабочие данные, платные тарифы и изменение видимости репозитория не требуются.

## Выбор площадки и ограничения

Проверены официальные [условия Render Free](https://render.com/docs/free): Python web service и TLS доступны; приложение засыпает после 15 минут без запросов, холодный запуск занимает время; локальные файлы исчезают при перезапуске. Доступно 750 часов сервиса в месяц на workspace. Лимиты сборок и исходящего трафика также применяются. Без платёжного метода превышение лимитов ведёт к приостановке; не включайте платное продление. Render Free PostgreSQL истекает через 30 дней, поэтому в этой конфигурации он не используется. Бесплатный сервис предназначен для демонстрации, не подтверждает производственную готовность.

[Neon Free](https://neon.com/docs/introduction/plans) предоставляет PostgreSQL: на дату проверки $0/месяц, 1 ГБ на проект, 100 CU-hours/проект, остановка вычислений после 5 минут простоя. Данные сохраняются отдельно от процесса Render. Квоты и доступность нужно повторно проверить при создании; не выбирать Launch/Scale. Вложения base64 и история расходуют квоту БД. Собственные резервные копии обязательны для продолжительной учебной проверки.

## Конкретные действия владельца

1. В своём аккаунте Neon создать **отдельный Free-проект** только для синтетических данных. Получить прямую PostgreSQL connection string с TLS (`sslmode=require`). Не публиковать её и не отправлять в переписку.
2. В своём аккаунте Render выбрать New → Blueprint, подключить `mln2k/hydroflow` и ветку `dissertation/flask-pages-2026-10-28`, использовать корневой `render.yaml`. Проверить `plan: free` и отсутствие платных ресурсов. Автодеплой выключен (`autoDeployTrigger: off`).
3. В защищённых переменных сервиса задать `DATABASE_URL` из Neon и новый `HYDROFLOW_ADMIN_PASSWORD` (12–128 символов); при необходимости изменить `HYDROFLOW_ADMIN_EMAIL`. Не использовать пароль из локального DEMO-ACCESS.txt.
4. Выполнить Deploy. Render задаёт `PORT` и `RENDER_EXTERNAL_URL`; `hydroflow.deploy` проверяет HTTPS origin, включает Secure cookie, ограничивает Host, применяет миграции и создаёт администратора **только если таблица пользователей пуста**. Повторный запуск не меняет пароль или данные. После первого входа удалить начальный пароль из окружения и сменить его через кабинет.
5. Открыть выданный Render URL, `/api/health`, войти. Создать синтетический проект и аккаунты нужных ролей через админпанель. Локальный генератор демонстрационных данных описан в README; он не подключается к хостингу.

Это оставшиеся действия владельца. Секреты вводятся только в панели площадки. Без них нельзя подтвердить URL, сохранность после реального перезапуска хостинга или восстановление на нём.

## Запуск и настройки

Build: `pip install -r requirements.txt`; Start: `python -m hydroflow.deploy`; healthcheck: `/api/health`. Версия Python в Blueprint — 3.12.14. Все Python-зависимости закреплены в requirements.txt. [Спецификация Blueprint](https://render.com/docs/blueprint-spec) использована для полей конфигурации; применение Blueprint в аккаунте ещё не проверено.

На другой площадке задайте `DATABASE_URL`, `PUBLIC_ORIGIN=https://ваш-домен`, `PORT`, начальные email/пароль и выполните ту же команду. SQLite этим модулем намеренно отклоняется. Waitress — реальный WSGI-сервер, один процесс/8 потоков, работает на Windows; [официальная инструкция Flask](https://flask.palletsprojects.com/en/stable/deploying/waitress/). Werkzeug используется только тестовой фабрикой сервера.

Forwarded-заголовки не считаются доверенными. Ограничитель входа использует адрес непосредственного соединения; за прокси он может быть общим для клиентов. Успешные входы не расходуют лимит, но для масштабирования нужен отдельный распределённый ограничитель и проверенная конфигурация доверенных прокси. Несколько процессов сейчас не поддерживают общий лимит входа. Это эксплуатационное ограничение, не обещание защиты от DDoS.

## Проверка после размещения и обновление

- Зафиксировать SHA, URL, время и версию схемы (1, 2); убедиться в HTTPS и Secure cookie.
- Выполнить вход/выход, чужой проект → 403, чужое обращение → 404, VIEWER не меняет проект; создать документ с вложением и второй версией.
- Перезапустить сервис: пользователь, проект, обращение и обе версии файла должны сохраниться. Повторить healthcheck и вход.
- Сделать `pg_dump --format=custom --file=hydroflow.backup --dbname=...`, используя защищённый `.pgpass`/интерактивный пароль. Восстановить через `pg_restore` в **новую пустую** тестовую БД; проверить числа записей, логин, файл и историю. Не применять `--clean` к рабочей БД.
- Перед обновлением сохранить дамп, выбрать проверенный commit, повторить проверки. Миграции сериализованы advisory lock в текущей PostgreSQL-схеме. `serve`/`init` также применяют миграции.
- Откат приложения не отменяет миграции. V2 добавляет таблицы; старые данные не переписаны. Для отката всей установки остановить запись, восстановить отдельную БД из дампа и переключить `DATABASE_URL` после проверки владельцем.

Локальное восстановление SQLite проверяется автоматически. Реальные `pg_dump`/`pg_restore` на Neon и испытания на Render остаются невыполненными до подключения аккаунта.
